## Summary

Talos Linux v1.14.5 (kernel 6.18.58-talos) for the **Mixtile Blade 3**
(RK3588) with **openmiop** built in: Ethernet (`omi0`) between the blades of
a Mixtile Cluster Box over its PCIe switch. Nothing has to be compiled.

**v0.7.2** is the Blade OS of OpenMIOP Stack v0.7.2: v0.7.1 on Talos
**v1.14.5**. DTB, U-Boot, the kernel command line and the openmiop code
(pcie-ep-net v0.7.1) are unchanged; the modules are rebuilt for the new
kernel, so the extension is now 0.7.1-v1.14.5.

* **Talos v1.14.5**: Linux 6.18.58, etcd 3.7.3, Go 1.26.10, and on-demand
  kernel module loading: when a driver asks for a helper module (for
  example DRBD for `drbd_transport_tcp`), Talos loads it by name, so such
  modules no longer have to be listed in `machine.kernel.modules`.
  Requests by alias are refused; the kernel log then shows lines such as
  `modprobe refusing to load "mdio:...": invalid module name` for the
  Ethernet PHY at boot, which is harmless (`end0` uses the built-in
  driver).
* The kernel tree for the openmiop modules follows siderolabs/pkgs
  `f4bda77` (Talos packages `v1.14.0-48-gf4bda77`), the extensions DRBD
  9.3.4, ZFS 2.4.4, iSCSI, Panfrost and Rockchip NPU are the v1.14.5
  builds.

Use it with
[ClusterBox firmware v0.4.4](https://github.com/roysbike/mixtile-clusterbox-mt7620a-openwrt/releases/tag/v0.4.4)
or v0.4.3 (no BMC change in this release).

Built by [GitHub Actions](@RUN_URL@) from commit `@COMMIT@`.
Changes: [CHANGELOG.md](https://github.com/roysbike/mixtile-talos/blob/v0.7.2/CHANGELOG.md).

`@OPENMIOP_REF@`: `openmiop-ep`, `blade3-nvme-recover`, `blade3-leds`),

## Supported hardware

Mixtile Blade 3 (RK3588), standalone or in a Mixtile Cluster Box.
Gateway pull and zero-copy need the BMC's `omi-rc` from pcie-ep-net
v0.5.0 or later: ClusterBox firmware v0.4.4 (recommended, see above),
v0.4.3, v0.4.2, v0.4.1, v0.4.0 or v0.3.0.

## Install a new node

As in [v0.3.0](https://github.com/roysbike/mixtile-talos/releases/tag/v0.3.0#install-a-new-node),
with this release's image and `machine.install.image: @INSTALLER@`. The
serial console must show `enabling system extension openmiop 0.7.1-v1.14.5`.

## Upgrade an existing node

One node at a time; mind etcd quorum; wait until DRBD and the databases
are healthy again before the next node.

```sh
talosctl -n <node> upgrade --image @INSTALLER@
```

* Keep the default drain (no `--drain=false`).
* Always pass `--image` and keep `machine.install.image` in the machine
  configuration equal to it; do not set
  `machine.install.grubUseUKICmdline: false` (the new kernel argument
  lives in the image's command line).
* Cordon a node that holds a CNPG primary first and wait for the
  switchover; move WAL-archiving primaries off a node with a local
  SeaweedFS volume server before draining it.
* If the node cannot pull the installer (`error pulling upgrade image`),
  load it with `talosctl -n <node> image pull --namespace system @INSTALLER@`
  and run the upgrade again.
* Same machine configuration as v0.7.1. Rollback:
  `talosctl -n <node> rollback`.

## Verification

```sh
talosctl -n <node> version                     # Tag: v1.14.5
talosctl -n <node> get extensions              # openmiop 0.7.1-v1.14.5
talosctl -n <node> read /proc/cmdline          # ... sysctl.net.core.default_qdisc=fq
talosctl -n <node> dmesg | grep openmiop       # "peer N up, ..., checksum offload"
```

`scripts/openmiop-verify.sh <node-ip>` checks all of this. The kernel log
still shows `module verification failed: signature and/or required key
missing - tainting kernel` once: the modules are not signed with the
Talos key.

## Tested

Lab Cluster Box, BMC on firmware v0.4.4, Cozystack v1.7.0. The test
installer from the same commit (branch `feat/talos-1.14.5`) on .108 from
2026-11-04: upgrade from v0.7.1 with the default drain in about three
minutes, three peers up (4 queues, doorbell, checksum offload),
`scripts/openmiop-verify.sh` 18/18, `blade3-nvme-recover` `unseen` 0,
DRBD (with `drbd_transport_tcp`) and ZFS 2.4.4 loaded, pools healthy,
`end0` at 2.5 Gbit/s; afterwards etcd 3/3, DRBD out-of-sync 0, CNPG
healthy and all LINSTOR satellites `Online`.

## Known limitations

* The BMC CPU is still the gateway limit (~200-280 Mbit/s to a blade).
* A BMC reboot drops every blade link for the length of its boot; with
  DRBD 9.3.4 check `out-of-sync:` 0 before
  ([LINBIT/drbd#153](https://github.com/LINBIT/drbd/issues/153)).
* One TCP flow uses one queue (~8.5 Gbit/s); four flows reach
  ~11.8 Gbit/s between two blades. No TSO/GSO.
* With traffic in both directions between two blades, ping rises to
  2-5 ms on average with peaks of tens of ms.
* `module.sig_enforce` stays off until the module is built and signed in
  siderolabs/pkgs.
