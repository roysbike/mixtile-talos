## Summary

Talos Linux v1.14.4 (kernel 6.18.57-talos) for the **Mixtile Blade 3**
(RK3588) with **openmiop** built in: Ethernet (`omi0`) between the blades of
a Mixtile Cluster Box over its PCIe switch. Nothing has to be compiled.

**v0.6.2** is the Blade OS of OpenMIOP Stack v0.6.2. Talos, the openmiop
driver (0.6.1-v1.14.4 from pcie-ep-net v0.6.1), DTB and U-Boot are the
same as in v0.6.1; what changes:

* **`fq` on omi0 from boot.** The kernel command line now carries
  `sysctl.net.core.default_qdisc=fq`, so omi0 comes up with `mq` and
  `fq` on each of its four queues instead of `pfifo_fast`. On the lab
  box, ping during four TCP streams between two blades dropped from
  3.5-3.8 ms to 0.36-0.94 ms. Setting `net.core.default_qdisc` in
  `machine.sysctls` does not reach omi0: the openmiop module creates it
  in the initramfs, before Talos applies the machine configuration.
* The README (EN/RU) was restructured, and the unused `patch/` directory
  from the old vendor build is gone.

Use it with
[ClusterBox firmware v0.4.1](https://github.com/roysbike/mixtile-clusterbox-mt7620a-openwrt/releases/tag/v0.4.1):
on v0.4.0, `nodectl status` (also run by `nodectl-metrics` and the LuCI
*Nodes* page) could wedge the PCIe fabric while a blade reboots, for
example during this upgrade. On v0.4.0, stop `nodectl-metrics` and keep
the *Nodes* page closed while you roll the blades.

Built by [GitHub Actions](@RUN_URL@) from commit `@COMMIT@`.
Changes: [CHANGELOG.md](https://github.com/roysbike/mixtile-talos/blob/v0.6.2/CHANGELOG.md).

Inside the image: Talos v1.14.4, kernel 6.18.57-talos, the v0.3.0 DTB and
U-Boot 2026.07, and the extensions openmiop 0.6.1 (pcie-ep-net
`@OPENMIOP_REF@`: `openmiop-ep`, `blade3-nvme-recover`, `blade3-leds`),

this build, not with the Talos key) and `sysctl.net.core.default_qdisc=fq`.
Image references: extension `@EXTENSION@`, overlay `@OVERLAY@`.
Kubernetes is not pinned by the image (tested with v1.34.3).

## Supported hardware

Mixtile Blade 3 (RK3588), standalone or in a Mixtile Cluster Box.
Gateway pull and zero-copy need the BMC's `omi-rc` from pcie-ep-net
v0.5.0 or later: ClusterBox firmware v0.4.1 (recommended, see above),
v0.4.0 or v0.3.0.

## Install a new node

As in [v0.3.0](https://github.com/roysbike/mixtile-talos/releases/tag/v0.3.0#install-a-new-node),
with this release's image and `machine.install.image: @INSTALLER@`. The
serial console must show `enabling system extension openmiop 0.6.1-v1.14.4`.

## Upgrade an existing node

One node at a time; mind etcd quorum; wait until DRBD and the databases
are healthy again before the next node.

```sh
talosctl -n <node> upgrade --image @INSTALLER@
```

* Keep the default drain (no `--drain=false`).
* Always pass `--image` and keep `machine.install.image` in the machine
  configuration equal to it; do not set
  `machine.install.grubUseUKICmdline: false` (the new kernel argument
  lives in the image's command line).
* Cordon a node that holds a CNPG primary first and wait for the
  switchover; move WAL-archiving primaries off a node with a local
  SeaweedFS volume server before draining it.
* Same machine configuration as v0.6.1. Rollback:
  `talosctl -n <node> rollback`.

## Verification

```sh
talosctl -n <node> version                     # Tag: v1.14.4
talosctl -n <node> get extensions              # openmiop 0.6.1-v1.14.4
talosctl -n <node> read /proc/cmdline          # ... sysctl.net.core.default_qdisc=fq
talosctl -n <node> dmesg | grep openmiop       # "peer N up, ..., checksum offload"
```

`scripts/openmiop-verify.sh <node-ip>` checks all of this. The kernel log
still shows `module verification failed: signature and/or required key
missing - tainting kernel` once: the modules are not signed with the
Talos key.

## Tested

Lab Cluster Box, BMC on firmware v0.4.1: the pull-request build of this
release (same sources, installer `sha256:bb00f6aa…`, CI checked the
kernel argument in the installer) rolled with drain on all four blades
on 2026-10-23, .108 first, then .133, .201, .204; CNPG primaries moved
off by cordon first. On every node openmiop 0.6.1 loaded, all peers up
with checksum offload, `scripts/openmiop-verify.sh` passed, and omi0 came
up with `mq` + 4 × `fq`. Afterwards etcd 3/3, CNPG healthy, DRBD in sync.

With `fq` on all blades, eight TCP streams on each of the 12 blade
pairs: 10.3-10.9 Gbit/s, ping during the load 0.66-2.3 ms on average
(max 2-12 ms); with `pfifo_fast` on the sender the same test gave
3.5-3.9 ms on average. Up to a few hundred TCP retransmits per 20 s run
(< 0.01 % of the segments), none dropped by `fq` itself.

## Known limitations

* The BMC CPU is still the gateway limit (~200-280 Mbit/s to a blade).
* A BMC reboot drops every blade link for the length of its boot; with
  DRBD 9.3.4 check `out-of-sync:` 0 before
  ([LINBIT/drbd#153](https://github.com/LINBIT/drbd/issues/153)).
* One TCP flow uses one queue (7.0-8.0 Gbit/s); four flows reach
  ~11 Gbit/s between two blades. No TSO/GSO. The driver has no byte
  queue limits yet, so latency under load still has tails of 13-30 ms
  with any qdisc.
* `module.sig_enforce` stays off until the module is built and signed in
  siderolabs/pkgs.
