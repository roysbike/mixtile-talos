## Summary

Talos Linux v1.14.4 (kernel 6.18.57-talos) for the **Mixtile Blade 3**
(RK3588) with **openmiop** built in: Ethernet (`omi0`) between the blades of
a Mixtile Cluster Box over its PCIe switch. Nothing has to be compiled.

**v0.7.1** is the Blade OS of OpenMIOP Stack v0.7.1, a fix release. Talos,
DTB, U-Boot, the kernel command line and the blade driver `openmiop-ep`
are the same as in v0.7.0; the openmiop extension is now 0.7.1-v1.14.4
from [pcie-ep-net v0.7.1](https://github.com/roysbike/pcie-ep-net/releases/tag/v0.7.1):

* **blade3-nvme-recover recovers after a short NVMe link drop.** On
  2026-10-31 the M.2 NVMe of a blade dropped its link by itself and was
  back at 2.5 GT/s within the module's 20 ms poll. The module did not
  see it, but the Root Port had lost its bus numbers and Memory/Bus
  Master enable and the NVMe its BARs: nvme marked the controller dead,
  the ZFS pool on it was suspended and the node needed a hard reset.
  The module now treats a Root Port without its secondary bus number or
  Memory enable as a link down and runs the usual recovery (restore the
  Root Port and NVMe config, raise the speed, reset the NVMe). New
  read-only parameter `unseen` (`/sys/module/blade3_nvme_recover/parameters/`),
  dmesg `link went down unseen (Root Port reset), recovering`.

Use it with
[ClusterBox firmware v0.4.3](https://github.com/roysbike/mixtile-clusterbox-mt7620a-openwrt/releases/tag/v0.4.3)
(no BMC change in this release).

Built by [GitHub Actions](@RUN_URL@) from commit `@COMMIT@`.
Changes: [CHANGELOG.md](https://github.com/roysbike/mixtile-talos/blob/v0.7.1/CHANGELOG.md).

## Supported hardware

Mixtile Blade 3 (RK3588), standalone or in a Mixtile Cluster Box.
Gateway pull and zero-copy need the BMC's `omi-rc` from pcie-ep-net
v0.5.0 or later: ClusterBox firmware v0.4.3 (recommended, see above),
v0.4.2, v0.4.1, v0.4.0 or v0.3.0.

## Install a new node

As in [v0.3.0](https://github.com/roysbike/mixtile-talos/releases/tag/v0.3.0#install-a-new-node),
with this release's image and `machine.install.image: @INSTALLER@`. The
serial console must show `enabling system extension openmiop 0.7.1-v1.14.4`.

## Upgrade an existing node

One node at a time; mind etcd quorum; wait until DRBD and the databases
are healthy again before the next node.

```sh
talosctl -n <node> upgrade --image @INSTALLER@
```

* Keep the default drain (no `--drain=false`).
* Always pass `--image` and keep `machine.install.image` in the machine
  configuration equal to it; do not set
  `machine.install.grubUseUKICmdline: false` (the new kernel argument
  lives in the image's command line).
* Cordon a node that holds a CNPG primary first and wait for the
  switchover; move WAL-archiving primaries off a node with a local
  SeaweedFS volume server before draining it.
* If the node cannot pull the installer (`error pulling upgrade image`),
  load it with `talosctl -n <node> image pull --namespace system @INSTALLER@`
  and run the upgrade again.
* Same machine configuration as v0.7.0. Rollback:
  `talosctl -n <node> rollback`.

## Verification

```sh
talosctl -n <node> version                     # Tag: v1.14.4
talosctl -n <node> get extensions              # openmiop 0.7.1-v1.14.4
talosctl -n <node> read /proc/cmdline          # ... sysctl.net.core.default_qdisc=fq
talosctl -n <node> dmesg | grep openmiop       # "peer N up, ..., checksum offload"
```

`scripts/openmiop-verify.sh <node-ip>` checks all of this. The kernel log
still shows `module verification failed: signature and/or required key
missing - tainting kernel` once: the modules are not signed with the
Talos key.

## Tested

Lab Cluster Box, BMC on firmware v0.4.3. A test installer with the same
openmiop code (branch `feat/nvme-recover-test`, pcie-ep-net 193ec6e) ran
on .108 from 2026-10-31: with `poll_ms` raised to 3000, a short Link
Disable pulse on the NVMe Root Port (the drop the module could not see
before) gave `link went down unseen`, link up after ~6 s, NVMe reset and
back `live` at 8 GT/s, with no I/O or ZFS errors; the pool stayed
ONLINE, DRBD out-of-sync 0 and the PostgreSQL clusters healthy.

## Known limitations

* The BMC CPU is still the gateway limit (~200-280 Mbit/s to a blade).
* A BMC reboot drops every blade link for the length of its boot; with
  DRBD 9.3.4 check `out-of-sync:` 0 before
  ([LINBIT/drbd#153](https://github.com/LINBIT/drbd/issues/153)).
* One TCP flow uses one queue (~8.5 Gbit/s); four flows reach
  ~11.8 Gbit/s between two blades. No TSO/GSO.
* With traffic in both directions between two blades, ping rises to
  2-5 ms on average with peaks of tens of ms.
* `module.sig_enforce` stays off until the module is built and signed in
  siderolabs/pkgs.
